PROJECT 01 / HEALTH TECH
Applied AI · Digital health

Arogya AI.

A digital health companion concept focused on helping people describe symptoms, organise health context, and reach a clearer next step through a structured conversation.

FlutterPythonFastAPIRule-based NLPAPI design
A+

01 / The problem

Health concerns are usually described in incomplete, unstructured messages. A useful digital experience needs to gather context, recognise what the person is describing, ask focused follow-up questions, and communicate uncertainty instead of pretending it does not exist.

02 / Product direction

The app concept brings symptom chat, patient context, history, and access to clinician consultation into one flow. The aim is a simpler first step for everyday health navigation—not an AI that replaces a doctor or makes a definitive diagnosis.

03 / Prototype scope

The Flutter interface has been built, with a Python/FastAPI backend and an early analysis pipeline. Current work focuses on improving the transition from free-text symptoms to useful structured analysis.

04 / How analysis works

  • Preprocess the message and identify symptom clues.
  • Route it toward relevant health categories.
  • Score and prioritise possible matches from available information.
  • Ask follow-up questions when context is insufficient.
  • Return a clear response while preserving uncertainty.

05 / Engineering priorities

Session state and predictable API contracts matter as much as answer text. Next improvements include stronger structured extraction, carefully sourced medical knowledge, realistic evaluation cases, escalation paths, privacy controls, and clinical oversight.

Prototype only—not a validated medical device. It must not be used for emergencies or as a substitute for professional medical care.

PROJECT 02 / VEHICLE SYSTEMS
Vehicle systems · Autonomy

ROCar.

A vehicle-focused engineering project. This case study explains the common autonomy/control architecture without claiming components, benchmarks, or completed features that have not been verified.

Vehicle systemsPerceptionMotion planningControlFeedback
R/C

01 / System flow

  • Perception: collect sensor input and extract useful environmental signals.
  • State estimation: create an estimate of vehicle position and motion.
  • Planning: choose a feasible path or next action.
  • Control: translate a plan into steering, speed, or actuator commands.
  • Feedback: compare the observed result with the target and adjust.

02 / Why the interfaces matter

A system can fail even when its parts work in isolation. Coordinate frames, stale sensor data, latency, control limits, and fault handling all need clear contracts and repeatable tests.

03 / Safety and testing

Real autonomy requires controlled experiments, predictable stop behaviour, recovery logic, and evaluation under noisy or missing sensor input. A visual demo alone is not evidence of a reliable vehicle stack.

PROJECT 03 / ROBOTICS
Robotics · Campus logistics

Autonomous
Delivery Kart.

A delivery-kart prototype exploring how a small mobile robot could move orders around a controlled campus environment by combining a route service, onboard sensing, navigation logic, and a backend workflow.

ESP32PythonComputer visionRoute APIsRobotics
A→B

01 / The use case

Short-range delivery in a campus or controlled facility is a useful robotics problem: the destination is known, the route is constrained, but localisation errors, obstacles, and people still make real movement difficult.

02 / End-to-end flow

  • A user or merchant submits a delivery task.
  • The backend validates the order and resolves a destination.
  • A route service or map graph supplies waypoints.
  • Onboard sensors estimate nearby conditions.
  • Navigation follows the path and reacts to obstacles.
  • Status updates report progress and exceptions.

03 / Planning versus control

Route planning selects the path over a map; a local controller uses live sensor feedback to move along it and slow or stop as conditions change. Camera-based detection can help, but it is not a complete safety system on its own.

04 / Hardware and software

The project explores an ESP32 hardware layer, camera/sensor input, Python-side vision and navigation experiments, and API integration. Perception, route planning, actuation, and task management should communicate through clearly defined interfaces.

05 / Key challenges

  • Localisation drift and recovery when a route is blocked.
  • Obstacle detection, stopping distance, and safe low-speed operation.
  • Network loss and predictable fallback behaviour.
  • Package access and clear delivery-state transitions.
  • Logging and repeatable route evaluation.

06 / Next engineering steps

Priorities include testing in a controlled environment, separating planning from actuation, recording route-success and intervention rates, and validating emergency-stop behaviour. A real-world deployment needs far more safety testing than a demo.

PRACTICE / ALGORITHMS
Competitive programming · C++

Understand first.
Optimise second.

A practice track for developing algorithmic judgement: model a problem, establish a correct baseline, prove it works, then improve time and space complexity.

C++Data structuresAlgorithmsComplexity analysis
O(n log n)

01 / Problem-solving loop

  • Restate the problem and identify constraints.
  • Work through examples and edge cases first.
  • Build a correct baseline, even if brute-force.
  • Choose a better data structure or algorithmic pattern.
  • Analyse worst-case time and space complexity.
  • Test boundary cases and explain correctness.

02 / Study areas

Arrays, vectors, sorting, binary search, recursion, hashing, greedy choices, two pointers, sliding windows, stacks, queues, linked lists, trees, graphs, and dynamic programming as the practice plan advances.

03 / What matters

The objective is not a decorative streak or an invented rating. It is learning to choose the right model, spot reusable patterns, and explain trade-offs in a solution.
